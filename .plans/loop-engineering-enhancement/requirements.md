# Loop Engineering 增强需求文档

## 背景

根据 Loop Engineering 最佳实践，我们需要补充以下核心能力，以实现真正的无人值守 AI 自动开发循环。

## 需求概述

### 核心组件（五大组件）

| 组件 | 作用 | 优先级 |
|------|------|--------|
| **自动化触发器** | 按时间/事件触发循环 | 🔴 高 |
| **Git Worktrees** | 多 AI 并行隔离工作目录 | 🟡 中 |
| **Skills (SKILL.md)** | 项目结构、规范、踩坑记录 | ✅ 已有 |
| **Hooks 系统** | 循环关键节点注入状态 | 🔴 高 |
| **状态文件** | 跨会话保存进度 | ✅ 已有 (agentmemory) |

### 失败模式对策

| 失败模式 | 问题 | 对策 | 优先级 |
|---------|------|------|--------|
| **假完成** | AI 自判完成 + 无客观验证 | 测试/lint 做硬关卡 | ✅ 已有 (pi-loop-engine) |
| **目标漂移** | 长对话丢失约束 | VISION.md 机制 | 🔴 高 |
| **自我偏好偏差** | 同个 AI 又写又查 | 对抗验证 | 🟡 中 |
| **理解债务** | 代码越堆越看不懂 | 代码审查 | 🟡 中 |
| **安全风险** | 未审即合入、权限膨胀 | 安全审计 | 🟢 低 |

## 详细需求

### 需求 1：VISION.md 机制

**目标**：防止目标漂移，确保 AI 始终围绕项目目标工作

**功能要求**：
1. 支持 VISION.md 文件定义项目目标、约束、禁止事项
2. 每次循环开始前重读 VISION.md
3. 检测当前任务是否偏离目标
4. 偏离时发出警告或停止循环

**文件格式**：
```markdown
# VISION.md

## 项目目标
构建一个高性能的 Web 应用

## 约束条件
- 不使用外部依赖
- 代码覆盖率 > 80%
- 响应时间 < 100ms

## 当前阶段
实现用户认证模块

## 禁止事项
- 不要修改数据库 schema
- 不要删除现有测试
```

**验收标准**：
- [ ] 支持 VISION.md 文件加载
- [ ] 支持目标漂移检测
- [ ] 支持注入到系统提示
- [ ] 有测试覆盖

---

### 需求 2：Hooks 系统

**目标**：在循环关键节点注入状态和检查

**功能要求**：
1. 支持多种 Hook 类型（循环前后、工具调用前后、错误时、提交前）
2. 支持 Hook 注册和执行
3. 支持 Hook 返回值控制流程
4. 支持 Hook 注入上下文

**Hook 类型**：
```typescript
type HookType = 
  | 'before_loop'      // 循环开始前
  | 'after_loop'       // 循环结束后
  | 'before_tool_call' // 工具调用前
  | 'after_tool_call'  // 工具调用后
  | 'on_error'         // 错误发生时
  | 'before_commit'    // 提交前
  | 'after_commit'     // 提交后
```

**验收标准**：
- [ ] 支持所有 Hook 类型
- [ ] 支持 Hook 注册和注销
- [ ] 支持 Hook 返回值控制
- [ ] 有测试覆盖

---

### 需求 3：自动化触发器

**目标**：按时间或事件自动触发循环

**功能要求**：
1. 支持 Cron 调度（定时触发）
2. 支持事件触发（git push、issue 创建等）
3. 支持文件监控触发
4. 支持停止条件

**触发类型**：
```typescript
type TriggerType = 'cron' | 'event' | 'file';

interface TriggerConfig {
  type: TriggerType;
  schedule?: string;      // Cron 表达式
  event?: string;         // 事件名称
  paths?: string[];       // 监控路径
  stopCondition?: () => boolean;
}
```

**验收标准**：
- [ ] 支持 Cron 调度
- [ ] 支持事件触发
- [ ] 支持文件监控
- [ ] 支持停止条件
- [ ] 有测试覆盖

---

### 需求 4：Git Worktrees 隔离

**目标**：多代理并行时隔离工作目录，避免文件冲突

**功能要求**：
1. 支持创建 git worktree
2. 支持清理 git worktree
3. 支持列出所有 worktree
4. 支持合并分支

**工作流程**：
1. 创建 worktree：`git worktree add <path> -b <branch>`
2. 代理在独立 worktree 中执行
3. 完成后合并分支：`git merge <branch>`
4. 清理 worktree：`git worktree remove <path>`

**验收标准**：
- [ ] 支持创建 worktree
- [ ] 支持清理 worktree
- [ ] 支持列出 worktree
- [ ] 支持合并分支
- [ ] 有测试覆盖

---

### 需求 5：对抗验证

**目标**：使用独立验证模型检查代码，防止自我偏好偏差

**功能要求**：
1. 支持代码生成代理
2. 支持审查代理（独立模型）
3. 支持对抗验证流程
4. 支持迭代改进

**工作流程**：
1. 生成代理编写代码
2. 审查代理独立审查（不同模型）
3. 如果发现问题，反馈给生成代理修改
4. 重复直到审查通过或达到最大迭代次数

**验收标准**：
- [ ] 支持生成代理
- [ ] 支持审查代理
- [ ] 支持对抗验证流程
- [ ] 支持迭代改进
- [ ] 有测试覆盖

---

### 需求 6：安全审计

**目标**：检测安全漏洞，防止安全风险

**功能要求**：
1. 支持 SAST 扫描（静态应用安全测试）
2. 支持凭证检测
3. 支持权限审计
4. 支持日志脱敏

**检查项目**：
- 凭证泄露（API Key、密码等）
- 路径遍历攻击
- 命令注入
- 权限提升
- 依赖漏洞

**验收标准**：
- [ ] 支持 SAST 扫描
- [ ] 支持凭证检测
- [ ] 支持权限审计
- [ ] 支持日志脱敏
- [ ] 有测试覆盖

## 风险评估

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| 实现复杂度高 | 高 | 分阶段实现，先实现核心功能 |
| 与现有扩展集成困难 | 中 | 使用统一接口，保持向后兼容 |
| 性能影响 | 中 | 异步执行，避免阻塞主循环 |
| 安全漏洞 | 高 | 定期审计，遵循最小权限原则
